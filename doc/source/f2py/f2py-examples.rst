F2PY examples
=============

Below are examples of F2PY usage that can serve as starting points for wrapping
your own code.

.. note::

   The best place to look for examples is the `NumPy issue tracker`_, or the
   test cases for ``f2py``. Some more use cases are in
   :ref:`f2py-boilerplating`.

F2PY walkthrough: a basic extension module
------------------------------------------

Creating source for a basic extension module
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Consider the following subroutine, contained in a file named :file:`add.f`

.. literalinclude:: ./code/add.f
    :language: fortran

This routine adds the elements in two contiguous arrays and places the result
in a third. The caller must provide memory for all three arrays. A basic
interface can be generated automatically::

    python -m numpy.f2py -m add add.f

This command will produce an extension module named :file:`addmodule.c` in the
current directory. This extension module can now be compiled and used from
Python just like any other extension module.

Creating a compiled extension module
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

You can also get f2py to both compile :file:`add.f` along with the produced
extension module leaving only a shared-library extension file that can
be imported from Python::

    python -m numpy.f2py -c -m add add.f

This produces a platform-compatible extension module that can be imported from
Python. It contains a method for each subroutine in ``add``. The docstring
shows the calling convention:

.. code-block:: python

    >>> import add
    >>> print(add.zadd.__doc__)
    zadd(a,b,c,n)

    Wrapper for ``zadd``.

    Parameters
    ----------
    a : input rank-1 array('D') with bounds (*)
    b : input rank-1 array('D') with bounds (*)
    c : input rank-1 array('D') with bounds (*)
    n : input int

Improving the basic interface
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The default interface translates the Fortran code literally: array arguments
become NumPy arrays, and the integer argument maps to a C ``int``. The
interface converts all arguments to the required types and shapes, raising an
error on failure. Because ``f2py`` knows nothing about argument semantics (that
``C`` is an output and ``n`` should match the array sizes), misuse can crash
Python:

.. code-block:: python

    >>> add.zadd([1, 2, 3], [1, 2], [3, 4], 1000)

This crashes on most systems because the lists are converted to arrays but the
underlying ``add`` function reads past the end of allocated memory.

To improve the interface, use ``f2py`` directives in a signature file. Start
from the default interface that ``f2py`` generates with the ``-h`` option::

    python -m numpy.f2py -h add.pyf -m add add.f

This command creates the ``add.pyf`` file in the current directory. The section
of this file corresponding to ``zadd`` is:

.. literalinclude:: ./code/add.pyf
    :language: fortran

Adding intent directives and size checks produces a Python interface that is
both easier to use and robust against malformed inputs.

.. literalinclude:: ./code/add-edited.pyf
    :language: fortran

``intent(out)`` tells f2py that ``c`` is an output variable to be created by the
interface before the Fortran call. ``intent(hide)`` removes ``n`` from the
Python argument list; its value comes from the size of ``a``. The
``depend(a)`` directive tells f2py that ``n`` depends on ``a``, so ``a`` is
created first.

After modifying ``add.pyf``, the new Python module file can be generated
by compiling both ``add.f`` and ``add.pyf``::

    python -m numpy.f2py -c add.pyf add.f

The new interface's docstring is:

.. code-block:: python

    >>> import add
    >>> print(add.zadd.__doc__)
    c = zadd(a,b)

    Wrapper for ``zadd``.

    Parameters
    ----------
    a : input rank-1 array('D') with bounds (n)
    b : input rank-1 array('D') with bounds (n)

    Returns
    -------
    c : rank-1 array('D') with bounds (n)

Now, the function can be called in a much more robust way:

.. code-block:: python

    >>> add.zadd([1, 2, 3], [4, 5, 6])
    array([5.+0.j, 7.+0.j, 9.+0.j])

Notice the automatic conversion to the correct format that occurred.

Inserting directives in Fortran source
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The same robust interface can be generated by placing variable directives as
special comments in the Fortran source.

.. note::

    This approach is preferred when the Fortran code is under active development.

If the source code is modified to contain:

.. literalinclude:: ./code/add-improved.f
    :language: fortran

Then compile the extension module::

    python -m numpy.f2py -c -m add add.f

The resulting signature for ``add.zadd`` is identical to the previous case. If
the original source had used ``A(N)`` instead of ``A(*)`` (and likewise for
``B`` and ``C``), adding only the ``INTENT(OUT) :: C`` comment would produce
nearly the same interface, with the difference that ``N`` becomes an optional
input defaulting to the length of ``A``.

A filtering example
-------------------

This example filters a two-dimensional array of double precision floating-point
numbers using a fixed averaging filter. It illustrates the advantage of using
Fortran for multi-dimensional array indexing.

.. literalinclude:: ./code/filter.f
    :language: fortran

Compile and link into an extension module named ``filter``::

    python -m numpy.f2py -c -m filter filter.f

The resulting module has a method ``dfilter2d`` that returns a filtered version
of the input.


``depends`` keyword example
---------------------------

Consider the following code, saved in the file ``myroutine.f90``:

.. literalinclude:: ./code/myroutine.f90
    :language: fortran

Wrapping this with ``python -m numpy.f2py -c myroutine.f90 -m myroutine``, we
can do the following in Python::

	>>> import numpy as np
	>>> import myroutine
	>>> x = myroutine.s(2, 3, np.array([5, 6, 7]))
	>>> x
	array([[5., 0., 0.],
           [0., 0., 0.]])

Instead of generating the extension module directly, first create a signature
file. This is a common pattern for multi-step builds. After running

.. code-block:: sh

	python -m numpy.f2py myroutine.f90 -m myroutine -h myroutine.pyf

the following signature file is generated:

.. literalinclude:: ./code/myroutine.pyf
    :language: fortran

Running ``python -m numpy.f2py -c myroutine.pyf myroutine.f90`` produces an
error because the generated signature file includes an unnecessary
``depend(m,n)`` statement for ``x``. Edit the file to read

    :language: fortran

Running ``f2py -c myroutine.pyf myroutine.f90`` now produces correct results.
